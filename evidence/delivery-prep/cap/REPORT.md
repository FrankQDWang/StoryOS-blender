# 30FPS 复测 — 2026-10-13

**结论：不采用到当前候选。** 带入创建／开书卡顿修复后，30FPS 可以减少每秒资源占用，但每帧 CPU 三组均上升，独立 Metal 样本的每帧 GPU 也未下降；开书／创建仍有约 55–60ms 帧间隔。原严格验收未通过，停止继续扩展限帧优化。根工作区仍是原帧率的 `codex/interaction-stalls`。

## 候选与方法

- 独立工作区 `.worktrees/cap-30fps-recheck`、分支 `codex/cap-30fps-recheck`。从 `f4979f7` 加入本轮卡顿修复，再接入旧 `37b95db` 的 FrameCap；原 cap 工作区没有修改。新增运行差异仅 FrameCap 与 Scene 接线，未改变资产、画质或动画公式。
- Chrome 无界面、1512×695、设备 DPR2、应用 DPR 上限1.5，同五书隔离数据；后台完成，不操作用户桌面。
- CPU 独立运行三个交替配对：实际主场景 `gl.render` 时间戳计数；CDP ProcessTime／墙钟为单核 CPU 百分比，ProcessTime／实际渲染帧数为 CPU ms/帧。关闭 GPU 查询。`cadence/` 保留全部逐帧数据。
- GPU 单独一对 Metal System Trace：目标 Chrome GPU 进程的 Active 区间并集，裁剪到记录的3.502秒窗口，包含浏览器合成。每帧除以该窗口的实际渲染次数，不把 command buffer 编号当帧，不使用 WebGL timer query。三个 CPU 配对已否定必要门槛，GPU 只作独立量化，未扩充成三对通过证明。
- `build-identity.json` 保存性能构建身份；`additional-build-identity.json` 保存固定截图修正入口与正常构建身份。根应用基线 SHA 在上级 `application-baseline.json`。

| CPU 单核百分比，三次 | 24.12 / 19.55 / 20.00 | 14.36 / 15.07 / 13.70 |
| CPU ms/渲染帧，三次 | 4.01 / 3.25 / 3.33 | 4.79 / 5.03 / 4.57 |

首页 CPU 百分比中位约下降28.2%；CPU每帧中位约上升43.9%。这符合“减少绘制次数可减少总工作量”，但不满足“每帧效率连续三次提高”的原要求。GPU仅一对，不能作稳定收益承诺。

## 保留的失败和工具修正

1. `smoke/` 首轮第二次进入时浏览器锁已生效，React提示尚未更新；脚本即刻断言失败。改为有界等待提示与锁同步，真实锁定／无按键环顾要求保持，修正后通过。
2. `visual/` 首轮创建两图差异超过门槛：固定入口传入paused，但构建转换只识别旧always表达式，候选以demand自行多推进了几帧。扩展测试构建转换，让固定入口从never启动且停用FrameCap；正式应用不变。完整11图复测通过，旧样本保留。
3. cadence首次脚本以任意elapsedTime回退退出1；基线创建两次触发。R3F `setFrameloop` 在demand→always时正常将elapsedTime重置0，不能当成负dt。原始回退字段和样本仍保留；脚本现在把它作为诊断，NaN／页面错误才直接失败。候选无此回退。
